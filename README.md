# Movie Memory

# Here is the git link:https://github.com/jashwanthreddykistipati-gif/movie-memory.git 

Movie Memory is a small full-stack app. You sign in with Google, tell it your favorite movie, and it shows you a fun fact about that movie generated by OpenAI. It's built with Next.js (App Router), React, Tailwind, Postgres, Prisma, Auth.js for Google OAuth, and the OpenAI API.

**I chose Variant A (backend: caching and correctness).** What interested me most in this assignment was getting the backend behavior right: not hitting OpenAI more than needed, handling several requests at once without creating duplicates, and still showing something useful when OpenAI fails. I preferred to spend my time on that instead of spreading it across UI work.

## Getting it running

```bash
cp .env.example .env      # fill in the values described below
npm install               # also runs "prisma generate" via postinstall
npx prisma migrate deploy # applies the migration to your database
npm run dev               # http://localhost:3000
npm test                  # backend tests (needs DATABASE_URL)
```

### Environment variables

- `DATABASE_URL`: your Postgres connection string. I used Neon with the direct (non-pooled) connection, but any Postgres works.
- `AUTH_SECRET`: a random string used to sign sessions. You can generate one with `openssl rand -base64 33`.
- `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET`: credentials for a Google OAuth web client. The authorized redirect URI needs to be `http://localhost:3000/api/auth/callback/google`.
- `OPENAI_API_KEY`: used on the server only and never sent to the browser.

### Database migrations

`npx prisma migrate dev` applies the migration in `prisma/migrations`. For a deployed database, use `npx prisma migrate deploy`.

### Tests

`npm test` runs Vitest against a real Postgres database. I wanted the locking behavior tested for real, so I didn't mock the database. The tests create throwaway users with `@test.local` emails and only ever delete those, so they won't touch real data. The OpenAI call is swapped for a fake function, which keeps the tests fast, free, and predictable.

## How it works

### User flow

The landing page at `/` has the "Sign in with Google" button. After logging in, you're sent to `/dashboard`. If you haven't picked a movie yet, the dashboard redirects you to `/onboarding`. Going to `/dashboard` or `/onboarding` while logged out sends you back to `/`. I do these checks inside the server components using `auth()`.

### Auth

I used Auth.js v5 with the Prisma adapter, so users and accounts are stored in Postgres, and JWT sessions. A session callback puts the database user id on `session.user.id`. Name, email, and photo are all optional in the schema. If Google doesn't give me a photo, the dashboard shows an initial instead, and if there's no name or email it shows a sensible placeholder.

### Data model

- **User** has the standard Auth.js fields plus `favoriteMovie`, which can be null. A null value means the user hasn't been onboarded yet, so I didn't need a separate flag.
- **Fact** has `id`, `userId`, `movie`, `content`, and `createdAt`, with an index on `(userId, movie, createdAt DESC)`. I store the movie on every fact so that changing a favorite movie later never mixes old facts with new ones. The index makes "latest fact for this user and movie" a single lookup. Facts are deleted along with their user.

### Onboarding

A server action validates the input with zod (trimmed, 2 to 100 characters) and updates the user. The user id comes from the session, never from the form.

### Fact generation

This is the main part, and it lives in `lib/facts.ts`:

1. Load the user's favorite movie from the database.
2. **Cache check.** Look up the most recent fact for this user and movie. If it's less than 60 seconds old, return it straight away. There's no lock and no OpenAI call on this path.
3. **Burst protection.** If a new fact is needed, I open a transaction and take a Postgres advisory lock (`pg_advisory_xact_lock`) keyed on the user and movie. Once I have the lock, I check the cache again, because another request may have just generated a fact while I was waiting. If so, I reuse it. If not, I call OpenAI and save the result. The lock lives in Postgres, so it also works when there are several server instances, which an in-memory lock wouldn't. It's released automatically when the transaction ends.
4. **Failures.** The OpenAI call has an 8 second timeout and no retries. If it fails, I return the most recent stored fact for that movie and flag it as stale so the UI can say so. If there's no stored fact at all, the API returns a friendly 503 message.
5. **Authorization.** `getFact` only takes the logged-in user's id, which comes from the session. `GET /api/fact` doesn't read any user id from the request, and every query is filtered by `userId`, so there's no way to ask for someone else's facts.

### Security

The OpenAI key is only read on the server. Movie input is validated on the server. The movie title is passed to the model as quoted data, with an instruction to ignore any instructions inside it, as a basic guard against prompt injection.

### Frontend

The dashboard is a server component that renders the profile and the movie. A small client component calls `/api/fact` and shows loading, error, and "showing a previous fact" states.

## Tradeoffs I made

- **The lock is held while OpenAI responds.** This is the simplest way to guarantee one generation per user and movie per window. The cost is that it holds a database connection for up to about 8 seconds. That's fine for this app, but I wouldn't do it on a high-traffic endpoint.
- **Concurrent requests wait instead of getting an "in progress" response.** It keeps the client simple, since everyone ends up with the same fact. The downside is slower responses during a burst.
- **The facts table doubles as the cache.** There's no separate cache table or cleanup job. The window means "60 seconds since the last generation", not a fixed clock window.
- **JWT sessions.** They avoid a database lookup on every request, but I can't revoke a session on the server before it expires.
- **Auth checks live in the pages, not in middleware.** This was simpler and worked well with the Prisma adapter. Middleware would redirect earlier.
- **Tests run against a real database.** That means the locking is properly exercised, but you need a Postgres to run them.

## What I'd do with two more hours

- Add rate limiting on `/api/fact` and a "new fact" button that respects the cache window.
- Set up a separate test database and a GitHub Actions workflow with a Postgres service.
- Switch to `pg_try_advisory_xact_lock` with a short wait, so one slow OpenAI call can't make a pile of requests queue up behind it.
- Add tests for onboarding validation and the redirects, plus an end-to-end test with Playwright.
- Let users change their favorite movie from the dashboard.
- Add structured logging, track OpenAI latency and failures, and store the model and prompt version with each fact.
- Move route protection into middleware and style the sign-in button for both light and dark mode.
